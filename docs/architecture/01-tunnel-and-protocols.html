Kontra · v4 architecture note · working draft

One tunnel for A2A agents and MCP servers

A node runs kontra connect. It serves what is on its localhost to a gate it chose, and calls what others serve through the same gate. The gate adds durable tasks, identity, policy and sealing. Nothing on the node listens on a public port.

1. The gateway story

Three ideas, in the order they were settled.

The gate is the product. It is an A2A server (and, now, an MCP server) toward anyone who calls, and an A2A/MCP client toward the servers enrolled behind it. It owns the task record and the policy. It never executes code, never holds a key that opens a sealed part, never opens a connection to a node.

One node type. There is no buyer sidecar and no seller sidecar. Every node runs one kontra connect, which dials out to a gate and does two things over that single connection: forwards the gate's inbound requests to servers on its localhost (hosting), and exposes the gate's catalog on its localhost so local clients can call out (hiring). A node that only hires has no --serve; a node that only hosts has local clients that never use port 7777. Same binary, same console, direction is a column.

Membership is which gate you dial. gateway.kontra.sh is the marketplace: the public, multi-tenant gate with a catalog and, in Cloud, escrow. A team's own gate is the same open-source binary with one tenant, no catalog and no money code. A node can hold several gate connections at once with one identity key enrolled at each.

What the gate holds, and what it refuses

Holds

Who may call what (API keys, tunnel keys, allow lists). Task records and the ordered event log. Tunnel sessions and which replica owns each socket. Bytes it does not interpret (sealed parts, blobs over 256 KiB in a bucket). In Cloud: listings, holds, receipts.

Refuses

To execute code. To store a private key that opens a part. To initiate a connection to a node (cancel travels inside the tunnel the node opened). To merge concurrent writes (a stale version is a 409). To route a request to a session whose key is not enrolled for that service.

2. How the tunnel works

The tunnel is a reverse HTTP proxy over one outbound connection. It carries ordinary HTTP/1.1 exchanges, so it does not care whether the bytes are A2A JSON-RPC, A2A HTTP+JSON or MCP Streamable HTTP. Each request from the gate is one multiplexed stream; a streaming response (SSE either protocol) stays on that stream.

Identity

On first run kontra connect generates one X25519 key at ~/.kontra/identity.key (0600). The same key proves possession in the handshake and is published as a sealing recipient for every service the node hosts. Enrollment binds a key_id to a service name at one gate, once, using a one-time token (kontra enroll <service> on a self-hosted gate) or the account's API key (Cloud). The binding lives in that gate's tunnel_keys table, so one key can be enrolled at several gates and revoked at each independently. When a node hires, it additionally mints a per-job X25519 key at send time; that key is what replies are sealed to, and it is deleted when the task is terminal plus any review window.

Several replicas, several nodes

Several nodes may enroll for one service (replicas). A new task picks a connected session round-robin and stays sticky to it for its life. Under several gate replicas, the replica holding the socket is the only one that can use it; Temporal routes the dispatch to that replica through a per-replica task queue (next section). If that socket dies mid-task, the task fails with tunnel_lost or retries per policy; the node never learns which tasks it was serving, because it holds no task state.

3. The Temporal primitive

Postgres is the task record and the replay log. Temporal is the clock and the durable dispatcher. Events never enter Temporal history: a streaming agent emits hundreds per task, and history is the wrong place for them. There is exactly one workflow type and four activities in the open-source gate.

The same primitive serves MCP without change. A task-augmented tools/call is a TaskLifecycle; tasks/get reads the projection; tasks/result blocks on LISTEN until terminal; notifications/tasks/status is one more subscriber. The only MCP-specific piece is in the dispatch activity: it polls the upstream server's own tasks/get at its pollInterval instead of consuming an A2A stream.

5. Tunneling MCP servers

MCP servers are the second kind of thing a node can host. The case for putting them behind the gate is the same as for agents, with one extra push: MCP over Streamable HTTP is now deployed widely, often on hosts that were never meant to accept inbound connections and with auth bolted on per server. Behind the tunnel the server listens on nothing public; the gate does bearer auth, allow lists, limits and audit once, for every server.

What differs from A2A is the session model. A2A is task-shaped; MCP is session-shaped (Mcp-Session-Id) with request/response tool calls, plus an experimental task shape since the 2025-11-25 spec. The gate maps each onto the primitive it already has.

Route and session affinity

The gate serves {public_url}/mcp/{name} as a Streamable HTTP MCP endpoint. initialize is forwarded; the gate records the upstream's Mcp-Session-Id, issues its own to the client, and pins the pair to the tunnel session it chose. Every later request with that id goes to the same node. If the session's tunnel dies, the gate returns 404 for that Mcp-Session-Id as the transport spec requires, and the client re-initializes; it lands on another replica if one is connected. For plain tools/call that is the whole story: the gate is a reverse proxy with auth and policy, and the node is a fixed-target forwarder.

Durable tool calls

When the upstream server declares capabilities.tasks.requests.tools.call and the client sends params.task, the gate owns the task. It answers with its own CreateTaskResult immediately, starts TaskLifecycle, and the dispatch activity forwards the task-augmented call upstream, then polls the upstream's tasks/get at its pollInterval, writing each status change as a task_events row. Client tasks/get reads the projection; tasks/result blocks on LISTEN until terminal and then forwards the upstream tasks/result; tasks/cancel is forward_cancel. The io.modelcontextprotocol/related-task metadata is rewritten to the gate's id the same way A2A ids are. Gate replica death, tunnel reconnect and client reconnect all behave as in section 3.

MCP Tasks are marked experimental in the 2025-11-25 spec and a SEP proposes moving them to an extension. Pin the spec version the gate speaks, as with the A2A TCK commit, and treat the task path as a capability the gate advertises only when the upstream does.

stdio servers

Most MCP servers people run locally are stdio processes. The node can own one: --serve mcp:fs=stdio:npx -y @modelcontextprotocol/server-filesystem ~/docs spawns it and bridges to the Streamable HTTP the tunnel carries. The gate never knows; it sees an HTTP target like any other.

Policy per tool

allow: stays the question "who may call this service". A second, optional list narrows which tools a principal may call: tools: { allow: ["read_*"], deny: ["delete_*"] }, matched on tools/call.params.name before dispatch, and applied to tools/list so denied tools are not advertised. A2A has no equivalent because skills are not callable units; the card is relayed whole.

What the marketplace sells

A listing gets a kind: a2a | mcp. The quote semantics differ: an agent is quoted per task; an MCP server is quoted per task-augmented call, or per session when it only offers plain calls. Escrow attaches only where there is a task to hold against, so a plain-call MCP listing is either free or metered later (the rails slot), not escrowed. That is a Cloud concern and does not touch the gate.

6. Syntax: no Kontra protocol, standard bindings

The decision under the prototypes was whether Kontra needs a wire protocol of its own. It does not, and every attempt at one (the v3 engine Protocol, the pull/lease sketch) was dropped for the same reason: a bespoke protocol means an SDK, and an SDK means sellers write Kontra code. With A2A and MCP as the only two protocols the gate speaks, an unmodified server and a stock client work on day one, and everything Kontra adds rides in the extension slots those protocols already have: A2A capabilities.extensions and metadata, MCP capabilities and _meta.

gRPC is the one binding the tunnel does not carry for free. yamux streams carry HTTP/1.1; gRPC needs HTTP/2. Two routes when it is wanted: terminate gRPC at the gate and speak JSON-RPC upstream (the gate is already a protocol translator for cards), or run h2c inside a yamux stream, which hashicorp/yamux permits but a2a-go's client would need to be told to use. Neither changes a node's setup, so it stays deferred.

What a node runs

# host one A2A agent and one stdio MCP server, hire through localhost:7777
kontra connect --gate https://gateway.kontra.sh \
  --serve a2a:hello=http://localhost:9999 \
  --serve mcp:fs=stdio:npx -y @modelcontextprotocol/server-filesystem ~/docs \
  --console          # http://localhost:7778

# a second gate, same identity key, enrolled separately
kontra connect --gate https://gate.team.internal --serve mcp:fs=http://localhost:8000

# only hiring: no --serve; the catalog appears on localhost:7777
kontra connect --gate https://gateway.kontra.sh

What a gate operator writes

listen: :8080
public_url: https://gate.team.internal
signing_key: file:./kontra.key
tls: { acme: { email: ops@team.internal } }
limits: { body: 4MiB, inflight_per_key: 32, rps_per_ip: 50 }
temporal: { address: localhost:7233, namespace: kontra }
postgres: postgres://kontra@db/kontra

services:
  hello:
    kind: a2a
    backend: { tunnel: {} }
    allow: [ "key:team-*" ]
    sealed: true
    task: { timeout: 2h, retries: 2 }
  fs:
    kind: mcp
    backend: { tunnel: {} }
    allow: [ "key:team-*" ]
    tools: { allow: ["read_*", "list_*"], deny: ["delete_*"] }
    tasks: passthrough        # durable | passthrough | off
  triage:
    kind: a2a
    backend: { a2a: { url: https://triage.internal:9000, allow_private: true } }
    allow: [ "org:team" ]

services: replaces agents:; the only new keys are kind, tools and tasks. In Cloud the block is empty and services come from the database.

What a client does

# stock A2A client, via the node
a2a send http://localhost:7777/agents/acme/hello "hi"

# stock MCP client config, via the node (sealing and per-job keys handled there)
{ "mcpServers": { "fs": { "url": "http://localhost:7777/mcp/acme/fs" } } }

# or straight at the gate with a bearer, no node (no sealing)
{ "mcpServers": { "fs": { "url": "https://gateway.kontra.sh/mcp/acme/fs",
                          "headers": { "Authorization": "Bearer kk_…" } } } }

8. Open questions

  • Name of the merged subcommand: kontra connect (used here) or kontra node.
  • Should the gate advertise MCP Tasks to clients when the upstream does not, running the task-augmented shape itself over a plain upstream call? It would make every tool call durable, at the cost of the gate holding results. Default here: no, mirror the upstream.
  • Session affinity on tunnel loss: re-initialize (spec-correct, loses in-flight state) or hold the client session for a grace period while the node reconnects with the same key. Default here: 404, let the client re-initialize.
  • Whether the per-tool tools: list belongs in allow: syntax (key:team-*:tools/read_*) or stays a sibling key as drawn.
  • gRPC: terminate at gate or h2c-in-yamux. Deferred until someone needs it.
