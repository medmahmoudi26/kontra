Kontra · v4 architecture note 2 · working draft

One CLI on your machine, gates as clusters

Nothing but kontra runs on a user's machine. Your agent or MCP server runs wherever you like, on localhost or in Docker. Every gate is a cluster: Kontra's public one, or a team's own.

supersedes the laptop inventory in note 1; v4 PRD §10 (embedded Temporal), §11 (kontra dev), §14 M4, §15 demo date 2026-10-24

1. What runs where

The earlier shape put a gate, an embedded Temporal and a Postgres container on the developer's laptop behind a kontra dev subcommand. A binary that drags five services onto your machine is not something people try on a Saturday. ngrok ships one small CLI and runs everything else as a service; Kontra does the same.

Your machine kontra

One static binary: connect, console (served by connect on :7778), login, seal, publish. Install by brew, curl | sh, or as a container image for a compose sidecar. The only state it creates is the identity key and per-job keys.

Your A2A agent or MCP server runs on localhost, in Docker with a published port, or anywhere the CLI can reach over HTTP. Unmodified.

Gates kontra-gate

Same Go module, second binary, shipped as a container image with a Helm chart and a three-container compose file. Never a laptop process and never a CLI subcommand. The five services live here, which is where five services belong.

Deleted kontra dev

Its two jobs are covered: people who want to play connect to the public gate; people who want to build the gate run the contributor compose. There is no third audience, so the subcommand, the embedded Temporal and the localhost-only rule go.

2. Playing with it: five minutes, zero infrastructure

brew install kontra
a2a serve --exec 'echo Hello World' --port 9999         # or your own agent, in docker or not
kontra connect --serve a2a:hello=http://localhost:9999   # --gate defaults to gateway.kontra.sh
#  → anonymous session · https://gateway.kontra.sh/agents/anon-7f3a/hello · expires in 2 h
#  → console http://localhost:7778
a2a send http://localhost:7777/agents/anon-7f3a/hello "hi"
#  → Hello World · visible in History on :7778, hosted and hired from the same laptop

Anonymous, ephemeral, rate-limited sessions on the public gate, the way ngrok hands out unauthenticated tunnels. kontra login (the existing magic-link flow) turns anon-7f3a into your name, makes it persistent and unlocks listings. The free tier is a tenant with tight caps, not a different binary. This also makes the first-user story a single machine: host and hire through one gate from one laptop, then invite a second machine.

Anonymous sessions need their own abuse controls, named in §12 of the PRD: 2 h TTL, per-IP session caps, no listings, no sealing recipients published beyond the session, the standard body and rate limits.

Agent in Docker

# CLI on the host, agent in a container with a published port
docker run -p 9999:9999 my/agent
kontra connect --serve a2a:hello=http://localhost:9999

# or the CLI as a sidecar in the same compose, no published port at all
services:
  agent:  { image: my/agent }
  kontra: { image: ghcr.io/kontra/kontra, command: connect --serve a2a:hello=http://agent:9999,
            volumes: [ "kontra-identity:/root/.kontra" ] }

Team gate on one VPS

# compose.yaml · three containers · kontra.yaml beside it
services:
  gate:     { image: ghcr.io/kontra/kontra-gate, ports: ["443:8080"], volumes: ["./kontra.yaml:/etc/kontra.yaml","acme:/acme"],
              command: serve -f /etc/kontra.yaml, depends_on: [temporal, postgres] }
  temporal: { image: temporalio/auto-setup, environment: { DB: postgres12, POSTGRES_SEEDS: postgres } }
  postgres: { image: postgres:17, volumes: ["pg:/var/lib/postgresql/data"] }

That is the whole self-host story: a VPS, one command, then everyone on the team runs the same kontra connect --gate https://gate.team.internal they would run against the public gate. One identity key, enrolled at each gate separately.

Contributors to the gate itself

Working on the gate's code still needs a Temporal and a Postgres nearby. That is the contributor compose in the repo, started with docker compose -f compose.dev.yaml up, plus go run ./cmd/kontra-gate. It is tooling for building Kontra, not for using it, and no one who only runs the CLI ever sees it.

4. What this changes in the v4 PRD

SectionChange
§4 Architecture"One Go binary" becomes "one Go module, two binaries": kontra (user) and kontra-gate (server image). Topology figure above.
§10 Data modelThe embedded-Temporal paragraph and the localhost-only refusal rule are removed. Anonymous sessions add tenant_id rows with an expiry.
§11 CLITwo tables. kontra: connect, console, login, seal, publish. kontra-gate: serve -f, enroll, migrate. The kontra dev row is deleted.
§12 SecurityAnonymous-session abuse controls as a named concern with a named test (anon_limits).
§13 OSS vs CloudCloud gains the anonymous and free tiers. OSS gains "team gate: Helm or compose" as its deployment story. The console runs on the CLI in both.
§14 MilestonesM4 "kontra dev with embedded Temporal" becomes "anonymous sessions on the public gate + compose file for team gates".
§15 AcceptanceThe README demo loses its gate terminal. "Runs from a clean machine" means a clean laptop against the public gate; a second test brings a team gate up from compose on a clean VPS and connects to it.

5. Open

  • Anonymous session TTL and caps: 2 h and a handful of concurrent tasks is the starting point; tune against abuse.
  • Whether the public gate should offer a pinned-version kontra connect --sandbox that lands on a separate, throwaway tenant pool, so marketplace tenants never share a replica with anonymous traffic.
  • Helm chart layout: one chart with Temporal and Postgres as optional dependencies, or the Cloud split (kontra-platform + kontra) reused as is.
