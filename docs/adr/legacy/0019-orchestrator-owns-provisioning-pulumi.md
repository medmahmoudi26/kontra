# 19. The orchestrator owns provisioning; OpenTofu is replaced by Pulumi

## Status

**Accepted.** Revises `CONTEXT-MAP.md`, which stated as a domain invariant that Execution never
provisions and that "a **Run** cannot cause a machine to exist". Deletes `infra/tofu/`. Does not
supersede any ADR; ADR 0018 is a hard prerequisite for the machine target (see Consequences).

## Context

Provisioning has been OpenTofu (`infra/tofu/main.tf`, the only provider-coupled file), with
Ansible configuring over SSH and `kontra fleet` shelling out to both. That layering is sound and
was debugged against three production incidents. Nothing about it is broken.

What it cannot do is live inside the orchestrator. HCL is not orchestrator TypeScript, so
"make a machine exist" can only ever be a subprocess the CLI shells out to on an operator's
laptop — never an operation the platform itself offers, observes, retries, or exposes over its
own API. Every other durable operation in kontra is a Temporal workflow with a server-minted id
and a queryable status; fleet provisioning was the one that was a shell command.

**The decision rests on co-location, not on a feature comparison.** On features Pulumi does not
clearly win: its DigitalOcean provider is auto-generated by `pulumi-terraform-bridge` from the
same `terraform-provider-digitalocean` OpenTofu already runs, so it drives identical machinery
with added release lag. Its DIY state backends are second-class by its own documentation. A
future reader comparing the two tools on capability will not find the reason here — the reason
is that Pulumi is a library, in the language the orchestrator is already written in, and
OpenTofu is a binary.

Three findings shaped the mechanism and would otherwise be re-discovered painfully:

1. **Pulumi's Node language host installs process-global `unhandledRejection` /
   `uncaughtException` handlers** for the duration of every inline run. An unrelated rejected
   promise elsewhere in the process fails the in-flight `up`, and Node's own crash handling is
   suppressed. Co-locating the engine with the Fastify API — which serves the SPA, runs DuckDB
   queries and S3 calls — is a correctness problem, not a tuning one.
2. **Pulumi's DIY lock has no compare-and-swap and no TTL.** A process killed mid-update leaves
   a lock file that wedges the stack permanently.
3. A ten-machine `up` takes minutes. `kontra fleet up` already waits up to 30×15s for SSH alone.
   That does not fit an HTTP handler.

## Decision

- **Pulumi replaces OpenTofu.** `infra/tofu/` is deleted. Pulumi programs are ordinary
  orchestrator TypeScript under `backend/src/infra/programs/`, written as **inline**
  Automation API programs so they can closure-capture a parsed `actor.json` rather than
  round-trip it through stack config as strings.
- **The engine runs in its own process**, `orchestrator-infra` — a fourth orchestrator role on
  the same image and its own Temporal queue. It is never `orchestrator-api`, for finding (1).
- **A Temporal Entity Workflow whose id is the stack's fully-qualified name is the mutex.**
  Workflow-id uniqueness — not Pulumi's lock file — is what makes a second concurrent writer
  structurally impossible. The lock file is a backstop, cleared only on activity retry.
- **`DIGITALOCEAN_TOKEN` lives in `orchestrator-infra`'s environment only**, passed to the
  workspace via `envVars` so it never lands in stack config or state. Every `/api/infra/*` route
  is `checkBearer`-gated from its first commit.
- **The control plane stays `docker-compose.yml`.** Pulumi provisions the Controller and runs
  `docker compose up -d --wait`; it does not manage the 12 services as resources. `orchestrator-api`
  is one of them, and the Docker provider replaces containers by delete-then-create — a spec
  change would delete the container running the engine, mid-update, holding the lock.
- **Building stays operator-side.** Only provisioning and placement move behind the API. Moving
  `docker build` server-side would require mounting the Docker socket into a service on the one
  machine holding the cloud credential.

The revised boundary: **Execution still never provisions.** No **Run**, and no code path
reachable from one, can cause a machine to exist — the infra queue is not addressable from a
graph. What changed is that the *orchestrator process family* now contains a Fleet-context role
alongside the Execution ones. That is a deployment fact; the models stay separate, and the test
remains the vocabulary — a sentence needing both a **Unit** and a **Machine** is crossing a
boundary.

## Consequences

- **Cloud authority widens, deliberately, and must be closed in the same change.** Provisioning
  previously required `DIGITALOCEAN_TOKEN` in an operator's shell; `infra/tofu/main.tf` kept it
  out of shell history, `ps` and state, and both `cli/fleet.go` and `cli/mcp_fleet_db.go`
  refused to read any provider credential at all. It now requires reaching a port on the
  Controller — where 26 of 31 existing routes are unauthenticated, a gap `backend/src/auth.ts`
  records in its own words. `checkBearer` on `/api/infra/*` is part of this decision, not a
  follow-up. `checkBearer` already fails closed with 503 when no token is configured.
- **The invariant that does not move:** the credential never reaches a worker machine, and
  authority to destroy a machine stays on the Controller. Fleet machines reach hostile
  third-party infrastructure; that boundary is the reason the split exists.
- **ADR 0018 becomes a prerequisite for the machine target.** A native install must otherwise
  reproduce daprd, placement and seven fixed ports in systemd — two processes ADR 0018 has
  already decided to delete. Sequenced after 0018, the native install is one static handler
  binary, the actor binary, and a Redis endpoint.
- **ADR 0011 digest pinning switches on for the first time on the fleet.** A machine-target
  actor has no image and therefore no git-SHA tag, so the content pin becomes the sha256 of the
  shipped **Bundle**, written to `KONTRA_ACTOR_DIGEST` — which nothing sets today, meaning
  admission pinning is currently and silently off. Stale code becomes a 409 at admission rather
  than a worker quietly running the wrong thing.
- **Ansible's rolling `serial: 3` health gate has no Pulumi equivalent** and must be rebuilt as
  batching inside the Entity Workflow, gated on the worker registering with Temporal. Until it
  exists, "a broken build stops at 3 machines instead of 20" is a property in flight.
- **Pulumi asserts convergence rather than re-converging.** `remote.Command` does not re-run when
  its inputs are unchanged and never inspects the host, so drift on a long-lived machine is
  invisible where Ansible would have repaired it. The **Watchdog** remains the only detector of
  a machine that is running but doing no work.
- The Pulumi CLI and provider plugins must be baked into the orchestrator image at pinned
  versions. Auto-download at boot repeats the failure class this repo has already paid for
  three times.
