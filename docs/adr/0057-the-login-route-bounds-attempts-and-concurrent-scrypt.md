# 57. The login route bounds attempts and concurrent scrypt

Date: 2026-10-06

## Status

**Accepted.** Completes the sign-in surface ADR 0045 introduced and **0054** scoped.

## Context

`POST /api/login` was careful about everything except volume. It gives one answer to every failure,
locks on a malformed stored hash, and verifies an unknown user against a decoy so timing reveals
nothing — and it had no bound on how often it could be asked.

That is two problems, not one, and the second is the one that was not obvious.

**Unlimited guesses.** scrypt makes one attempt expensive and says nothing about a million of them.
The install's first password is generated by `kontra init` and is not in a wordlist, but
`kontra user add` takes whatever an operator types.

**The control plane's I/O.** `node:crypto`'s `scrypt` does not run on the event loop. It runs on the
**libuv threadpool**, which defaults to four threads and is shared with every `fs` and `dns` call
the process makes. Each verification holds a thread for ~150 ms and 32 MiB. A few hundred concurrent
unauthenticated requests therefore queue ahead of *every file read in the orchestrator* — the served
bundle, the audit log, `config.yaml`. And the decoy-hash defense **amplifies** it: because an unknown
user is verified too, an attacker needs no valid username to cause the work.

So the route's timing defense, which is correct, made its availability worse. That is why the fix is
not "rate limit the login" alone.

## Decision

**Two bounds, for the two different problems, both checked before any scrypt runs.**

| | bounds | protects |
|---|---|---|
| the gate | concurrent verifications (2) | the threadpool, and therefore the whole process |
| the bucket | attempts per source per window (10/min) | the password |

A limiter that rejects *after* doing the expensive thing is not a limiter; it is a log line.

### One method, not an `admit()` plus a `run()`

`LoginGuard.attempt(source, work)` counts, reserves and runs in one call. The obvious two-call shape
has a hole: the reservation would live in `run`, so if an `await` ever appeared between the two — a
log line, an audit write, an innocent refactor — every request in a flood would pass `admit` while
the in-flight count was still zero, and the gate would admit all of them. The bound would read as
enforced and hold nothing. Reserving and running together cannot be sequenced wrongly, so the hazard
is not a rule anybody has to remember.

### Per source, not per username

Keying attempts on the submitted name is the stronger defense against someone grinding one known
account. It is deliberately **not** taken, for two reasons:

- It hands anybody a **lockout**: ten wrong guesses at `admin` and the operator cannot reach their
  own box.
- It reintroduces the **enumeration oracle** the route exists to avoid. A limit that engages per name
  is observable, so "which names exist" becomes answerable by watching which keys throttle.

`req.ip` is Fastify's socket peer and `trustProxy` is off, so it is the kernel's view of who
connected and cannot be set by a header. On a loopback appliance it is `127.0.0.1` for everything,
which makes the bucket effectively global — correct for a single-operator install rather than a
shortcoming, since the attacker and the operator share the address, so the shared budget is the one
that matters.

### 429, and the same body as a refusal

**401 signs the console out** (`packages/core/src/run/session.ts` clears its token on one), so a
rate limit spelled 401 would end the operator's session and read as an orchestrator restart — the
same reasoning as ADR 0054's scope refusal.

The throttled body is byte-identical to the 401 body. A distinct message would confirm to an
attacker that they had found the limit, which is the only feedback this route gives that does not
depend on knowing the password. The saturation case (`busy`) does say so, because it is a statement
about the box and not about any credential.

### Success forgives

The first password is generated and long, so fumbling it is the expected case, not the suspicious
one. Without `forgive`, an operator who mistypes nine times and then succeeds spends the rest of the
window locked out of a box they just proved they own.

## Consequences

- **An attempt is counted on the way in, not on failure.** Counting only failures would let an
  attacker run the threadpool flat for free, since every guess in a guessing attack is wrong. This is
  what makes `forgive` necessary rather than merely kind.
- **Shedding does not refund the attempt.** Deciding is not free either, and a refund would make
  saturation a way to attempt without being counted.
- State is in memory and dies with the process, like `sessions`. A restart forgives every bucket.
  The alternative is a Redis dependency in the sign-in path, and sign-in has to work when Redis does
  not.
- **No new npm dependency.** `@fastify/rate-limit` would add a package to the control plane to count
  to ten on a single-instance install.
- A throttled attempt is an audit event, with `too-many-attempts` and `busy` distinguished in
  `target` — a flood's only trace that outlives the container's stdout.
- **Not addressed here:** the bucket is per-process, so a future multi-replica orchestrator would
  give each replica its own budget. Single-instance is the documented deployment (ADR 0047).

## Tests

`control/orchestrator/src/auth/loginGuard.test.ts` (14) and five added to
`control/orchestrator/src/routes/login.test.ts`.

The assertion that matters most is that **a refusal does no scrypt** — several unit tests drive the
guard with a thunk that records whether it was called, because "did the work happen" is the property,
not what was returned. Also pinned: the gate's peak concurrency never exceeds its setting; a thunk
that throws still returns its slot (without the `finally`, the gate closes permanently after two
malformed hashes); the throttled body equals the refused body; 429 is never 401; and one address
cannot spend another's budget.

The route tests use cheap cost parameters (`N: 2`). They assert the guard's bookkeeping, which does
not depend on the work factor, and at the real N=32768 they ran scrypt ~55 times and made the file
the slowest in the suite at 20s — now 1.6s. The tests that are about the credential itself keep the
real cost.
